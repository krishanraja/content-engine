# Mindmake Video and Carousel Studio: where it is right now

## What it is

Mindmake Video and Carousel Studio is the governed production engine behind Mindmake's publication: it turns an approved editorial brief into deterministic Shorts and swipe carousels for The Money of AI and Built With AI, and nothing renders, packages or uploads until Krish has approved the exact artifact hash. It is a TypeScript and Remotion studio with a hash-locked Python transcription runtime, a Windows Scheduled Task runner that executes Control Center commands without any chat session, and a carousel director that shares the video engine's evidence, approval and learning rules while using its own story, slide and render contracts. Codex, Claude Code, Claude.ai, ChatGPT and Control Center are windows into the same engine (`docs/ENGINE_SESSION.md`); a repository checkout gives instructions, not production authority. The studio optimises honest reach, retention, sharing and qualified action. It never publishes publicly: YouTube upload is private-only, and LinkedIn, TikTok and Instagram output stay local packages for a human to post (`AGENTS.md`). In the Content Engine registry this repo is `video-studio`, "the bespoke AI video production agency: a governed render engine, carousel engine and review surface".

## Who it is for and why it matters for Mindmake

The studio is not sold. It is the production system behind what Mindmake does sell and publish, and it is a proof asset. The room_face buyer (`control-center/docs/ICP.md`: a senior leader at a PE or VC backed media, adtech, publishing or data business, quietly behind on what is coming and unable to say so inside their organisation) runs a media business and is watching one person build a governed, deterministic production pipeline in which every taste rule needs explicit approval. What this repo proves is that AI production can be governed rather than merely generated: the machine proposes, the record shows why, and a person decides against an exact hash.

Stories a writer can carry without asking Krish:

- **A rule becomes taste only when a person says so.** Feedback moves through `observed`, `inferred`, `confirmed`, `trial`, `eligible`, `user_approved`, `active`. A rule is active only after the exact rule appears in reviewed Git configuration, and views alone can never make one eligible (`docs/ARCHITECTURE.md`, "Learning boundary"). Codex and system diagnostics are observations and cannot become taste rules.
- **The first rendered carousel was rejected, and the record says why.** Repeated dark backgrounds, generic boxes, inert space and duplicate series labelling failed the standard "even though deterministic tests passed" (`docs/CAROUSEL_DECISIONS.md`). Three replacement concepts went to two blinded judges; the approval-interlock spine won 72.0 and 71.5 out of 80 (`docs/CAROUSEL_RESET_TRACE.md`).
- **Fail closed beats shrink to fit.** Every branded render must show the official wordmark's real lettering at 50 render pixels or more; if no collision-free placement exists, rendering and QA fail rather than covering Krish or shrinking the mark (`README.md`).
- **The machine keeps evidence, not transcripts.** The session contract records tool-backed actions, exact feedback excerpts and artifact differences, and never a whole chat transcript. Silence is not feedback (`docs/ENGINE_SESSION.md`).
- **Nothing publishes itself.** A merged code change is not an installed runner, and an installed runner is not a live integration until seven named steps succeed (`docs/DEPLOYMENT.md`).

Objection it answers: "AI content is slop." Here is a pipeline that refuses to make the video when the source cannot clear the bar, and writes down the refusal.

## What changed recently

- 2026-09-07 **Runner consumes approved production briefs** (PR #39, `8477f04`). Why: production had to start from an approved Content revision without a person in a chat; the change "lets the installed runner claim briefs without a live Codex, Claude, or ChatGPT session", "materializes deterministic short-native jobs and pauses extract/solo work for a reviewed Drive source bundle", and "preserves manual CLI import as offline recovery". Import is content-addressed and idempotent, so "a changed brief cannot reuse an existing brief ID", and carousel-only briefs are "imported without inventing a video job" (`docs/OPERATIONS.md`). Verification note from the PR: "383-test suite: 382 pass; one 10.1s Windows cold-start timeout corrected to a finite 20s bound, then the CLI suite passed."
- 2026-09-07 **Carousel director** (PR #36, `9797a03`, `97022f8`, `e6f4865`, merged as `efb3f80`). Why: evidence, series canon, approval lineage and feedback memory are shared with video, but "story pacing, image roles, output geometry and packaging are not". A separate repo was rejected because "it would duplicate governance and split preference learning". The first rendered treatment was rejected for repeated dark backgrounds, generic boxes and duplicate Built With AI labelling although every test passed; two blinded judges then chose the approval-interlock spine (72.0 and 71.5 of 80). Krish moved the Mindmake signature to bottom-left after finding that transparent source-canvas edges had caused false visual alignment. The same review story rendered twice to identical image hashes. Gate: the rendered placement still needs Krish's approval (`docs/CAROUSEL_DECISIONS.md`).
- 2026-09-07 **Approved briefs before production** (PR #38, `b1e5a78`). Why: it "prevents raw radar signals from becoming production ideas, and records the retirement of the chat pulse in favour of pull-only Control Center delivery". The pulse config gives the reason: "Editorial opportunities and runner attention belong in the pull-only Control Center Content surface, not an attached chat."
- 2026-09-07 **Portable Studio session contracts** (PR #37, `0c4b380`). Why: any supported LLM or Control Center should be a window into one engine, but "connecting this repository is necessary but not sufficient"; only a tracked gateway session grants mutation and learning capture, and the gateway stores structured events, never a whole transcript. The PR notes "the first local full parallel Windows run hit existing filesystem timing limits" while GitHub's clean Ubuntu and Windows runs passed.
- 2026-09-06 **Runner recovery after Windows interruptions** (PR #35, `4bf6234`). Why: Windows can terminate the daemon during sleep, an update or a session transition, so a five-minute recovery trigger sits beside the at-logon trigger, and a synced non-secret Inbox marker keeps Drive folder identity across ordinary remounts while a genuinely changed identity still fails closed. Real task readback: two triggers, PT5M interval.
- 2026-09-05 **Chain-safe projection acknowledgements** (PR #32, `7762a4f`). Why: the acknowledged platform cursor had to be separated from magic-edit undo ancestry, pending receipts made crash-safe, and the Scheduled Task registered as the directly owned Node daemon instead of a PowerShell to npm to tsx wrapper chain that could orphan a process. Protocol v1 has one stable runner identity and no in-place signing-key rotation. 41 test files, 355 tests.
- 2026-09-05 **Runner source virtualisation** (PRs #30 and #31, `084322f`, `1f62057`). Why: "Packaged applications can virtualize LocalAppData while npm records workspace junctions and runtime state against the logical path. The resulting checkout can look complete while Node cannot traverse its internal packages, and an outside Scheduled Task can see a different Python or job root." Source and runtime moved to explicit Documents paths with a copy-only migration; #31 fixed the install order so migration runs before the preflight.
- 2026-09-05 **Governed Drive Inbox discovery** (PR #29, `682ee4f`). Why: recordings should be found without anyone scanning the Drive root; a file must sit unchanged across two scans and 30 seconds before it is hashed, a replaced mount fails closed until Krish rebinds, and discovery "never renders, packages, uploads, publishes, or sends media and local paths to Control Center". 40 files, 307 tests.
- 2026-09-05 **Runner stays alive on battery, fails closed on drift** (PRs #27 and #28, `681a25f`, `e81d62d`). Why: the task must survive a switch to battery, so both battery settings are read back after registration and the task is disabled if either drifted. "Battery resilience does not turn the Windows host into an always-on cloud worker."
- 2026-09-04 **Runner lock identity** (PR #26, `6180173`). Why: "The first runner-lock test on merged main spent its entire 5-second budget starting legacy Windows PowerShell to inspect the current process.
